# CVHome Infrastructure Architecture Proposal

## Context

`cvhome/.agents/requirments/arch.md` asks for a review and modernisation of CVHome's deployment
architecture, and is explicit that **phase one is discovery and architecture, not a rewrite**. This plan
covers that phase only: produce the architecture proposal the document specifies. Implementation is gated
on your approval of it.

**Nothing is currently deployed.** The three infra repos are unprovisioned legacy code. That removes
arch.md's migration constraints entirely — no imports, no resource reuse, no downtime budget — so the
target architecture is designed from scratch on its merits, and arch.md's *Migration Plan* section is
replaced by a **Build & Rollout Plan** (zero to running).

Discovery is done. The legacy code is not merely dated — it could not deploy the current application even
if it were applied. The app ships **15 deployable services**; the Terraform knows **11**, four of those
under stale names:

| App service (`common-config.yml`) | Port | Legacy Terraform |
|---|---|---|
| `store-core-gateway`, `uaa` | 8000, 8001 | present |
| `tenancy` | 8020 | present as **`control-plane`** |
| `console-ui` | 8011 | present as **`seller-ui`** on **port 8010** |
| `billing` | 8021 | **absent** |
| `pod-registry` | 8022 | **absent** |
| `spg`, `landing-ui`, `merchant`, `catalog`, `checkout`, `cua`, `payment` | 80, 8110, 8120, 8122–8125 | present |
| `content` | 8121 | **absent** |
| `inventory` | 8126 | **absent** |

Six ECR repositories are likewise missing from `bootstrap.yaml`, and ECR does not create repositories on
push — so the image build would fail before Terraform was ever reached.

## Decisions locked in

1. **Proposal only** this turn. No infrastructure is written until you approve.
2. **New repo**, replacing `cvhome-bootstrap` + `cvhome-infra` + `cvhome-store-pod`.
   `cvhome-common-ecs-service` stays a separate, **tag-pinned** module repo. `cvhome-secrets` is dropped.
3. **Per-pod RDS.** Isolation over cost; cost levers found elsewhere.
4. **CodeBuild is the canonical deployer.** GitHub Actions drops to plan-on-PR.
5. **Your two-step model is structural**: step 1 establishes *config and flavour*, step 2 provisions from it.
6. **Greenfield.** No migration, no backward compatibility with the legacy repos.

## Deliverable

One document at **`cvhome/.agents/plans/infra-target-architecture.md`**, also published as an Artifact for
review and sharing. It follows arch.md's required structure, with the one substitution noted above.

## Proposal content — the substance to be written

### 1. What we are replacing, and the lessons that shape the target

arch.md asks for the existing state to be documented and its technical debt identified. Since none of it
runs, this section is short and serves one purpose: each defect below maps to a design rule in §2, so the
new architecture is answerable to something concrete rather than to taste.

- **Service drift** — the table above. *Rule: one catalog, machine-read, drift-checked in CI.*
- **Duplication** — `store-pod-cluster.tf` is 654 lines because ~25 identical env vars are copy-pasted into
  six service blocks; a new service costs ~60 lines. *Rule: env computed once, services generated by
  `for_each`.*
- **Two divergent deploy paths** — bootstrap/CodeBuild derives `project` as a random 4-char id; the GitHub
  Actions workflows derive it as `cksum(account-owner-region)`. Different ids, different state. The Actions
  path reads an SSM parameter only the bootstrap creates, and passes `TF_VAR_env` / `TF_VAR_image_tag` /
  `TF_VAR_docker_registry`, none of which `params.tf` declares — silently ignored. The app's own publish
  workflow uses the `cksum` scheme, so images land where Terraform never looks. *Rule: one deployer, one
  project id, resolved from one place.*
- **No environment dimension** — `env` is hardcoded `"dev"` in the bootstrap SSM payload
  (`bootstrap.yaml:451`). One stack is one environment and it can only be dev. *Rule: env is a first-class
  parameter; flavour carries the rest.*
- **Renames that broke routing** — the ALB has a `seller-ui.<domain>` rule and Route53 record, but
  `GatewayRouteLocatorImpl` only accepts `console-ui.<domain>`. The Stripe webhook is registered at
  `/subscription/api/v1/stripe-webhook/public/events` (`bootstrap.yaml:805`), a path that did not survive
  the tenancy/billing split; the real one is `/billing/api/v1/stripe-webhook/…`. The Stripe key is injected
  into `tenancy`, but Stripe now lives in `billing`. *Rule: hostnames, routes and secret bindings derive
  from the catalog, not from hand-maintained lists.*
- **Dead knobs and dead wiring** — `pod_size` is threaded SSM → pod object → module variable and never read
  (four values in the console that do nothing). `private_subnets` passes through three module levels
  unused. `random_password.password` is generated and never referenced. `health_check`, `priority`,
  `service_type`, `load_balancer_host_matchers` are declared in the shared module and never consumed. The
  entire `cvhome-secrets` repo is read by nothing, and its `bcrypt()` locals re-hash every plan, so it
  would show a permanent diff. *Rule: every input is consumed or absent.*
- **Reproducibility** — modules sourced `git::…?ref=main`; an apply can change behaviour with no commit.
  *Rule: pin by tag.*
- **Security** — tasks in public subnets with public IPs; RDS `publicly_accessible = true`; task roles with
  `s3:*`, `ssm:*`, `secretsmanager:*` on `*`; deploy role with `PowerUserAccess` **and** `iam:*`.
- **Reliability** — `FARGATE_SPOT` weight 100 with no on-demand base, `desired = 1` throughout, circuit
  breaker disabled, `health_check_grace_period_seconds = 0` on Spring Boot services, RDS with
  `skip_final_snapshot`, no backups, no deletion protection.
- **No right-sizing** — all 15 services identically 512 CPU / 1024 MB / 1 task.
- **Stale identifiers in the app** — `fargate-config.yml` pins a real `namespace-id: ns-je7qri6wn7fbsrpn`
  and a `store-pod-507f1f77` namespace; these must become environment-supplied.

### 2. Target Architecture

**a. Platform: ECS Fargate + Cloud Map, kept deliberately.** Now genuinely open, so it gets a decision
record rather than an assumption. It stays because the *application* is ECS-native: `store-commons/
ecs-commons/ecs-service-discoveryclient` resolves `lb://` through Cloud Map `DiscoverInstances`, and there
is a `fargate` Spring profile and a `fargate-task-info` module. EKS adds a $73/mo control plane and real
operational weight for no capability CVHome needs; App Runner has no Cloud Map service discovery and cannot
do the raw TCP 80/443 passthrough `spg` requires for Caddy's on-demand TLS. Changing platform means
rewriting application code, which arch.md's cost and simplicity priorities do not justify.

**b. Service catalog — the central mechanism.** One `services.yaml` is the single source of truth for name,
port, layer, image, database need, CDN need and edge. Terraform `for_each`es it into ECR repositories, ECS
services, task definitions and env vars; common env is computed once into a `local` and merged with
per-service extras. The 654-line pod file becomes roughly 150. Adding a service is one catalog entry. A CI
job diffs `services.yaml` against the app's `common-config.yml` and fails on drift — precisely the failure
that left four services with no infrastructure.

**c. Flavours — your two-step model, made structural.** Replace the scattered `is_prod` / `is_monitoring` /
`pod_auto_scale` / `pod_size` flags with one named **flavour** (`dev`, `staging`, `prod`, `ephemeral`)
fixing task CPU/memory, desired counts, Spot-vs-on-demand, RDS class and backup policy, log retention and
monitoring — each key individually overridable. `pod_size` becomes a real per-pod flavour instead of a dead
knob.

- **Step 1 — Bootstrap (CloudFormation, one click).** Chooses the flavour, collects the few real inputs
  (hosted zone, **env name**, pod count, pod size, Stripe key), writes the environment's config record to
  SSM, creates only what Terraform cannot create for itself — state bucket, deploy role, CodeBuild
  projects — and then *starts* the pipeline. Nothing triggers CodeBuild in the legacy template, which is
  why its "one-click" deploy stops halfway.
- **Step 2 — Provision (Terraform, run by CodeBuild).** `prereq` state (ECR + ACM, from the catalog) →
  image build → `env` state (everything else).

  *Alternative for your call:* keep ECR in CloudFormation via the `AWS::LanguageExtensions` transform and
  `Fn::ForEach` over the catalog, avoiding the two-stage apply — at the cost of the catalog existing in two
  formats. Recommendation is the two-stage apply; one source of truth wins.

**d. Environments.** `project` becomes a stable, settable id rather than random 4 chars; `env` a real
parameter. Resources are named `${project}-${env}-*`. State at `env/<env>/terraform.tfstate` with **S3
native locking** (`use_lockfile`, Terraform ≥ 1.10) — no DynamoDB table, no extra cost. Config layering:
SSM holds what bootstrap generates, `envs/<env>.tfvars` holds what humans choose, tfvars wins. Someone who
never touches git still gets a working environment; a team that does gets reviewable diffs.

**e. Repository structure** (new repo, suggested name `cvhome-platform`):

```
bootstrap/bootstrap.yaml     services.yaml            # the catalog
modules/{store-core,store-pod,network}/               # ecs-service stays external, tag-pinned
envs/{dev,staging,prod}.tfvars
main.tf variables.tf outputs.tf backend.tf
```

**f. Store-pod.** Per-pod RDS as you chose. The per-pod NLB is retained and the document explains why it
cannot be shared: `spg` terminates TLS with Caddy on-demand certificates for custom tenant domains, which
SNI routing on a shared NLB cannot express. It flags — without proposing it now — that a per-environment
`spg` fleet backed by `pod-registry` would collapse those NLBs, but that is an application change.

**g. Secrets.** RDS-managed master user secret. One Secrets Manager secret per concern under
`/${project}/${env}/`. Task IAM scoped to those ARNs rather than `*`.

**h. Security and reliability**, correct from day one rather than retrofitted: per-service security groups
on the service's own port instead of 0–65535; RDS not publicly accessible; private subnets with a single
NAT gateway **under the prod flavour only** (dev/staging stay public-subnet — NAT at ~$33/mo/AZ is not worth
it there, and VPC interface endpoints are not cheaper); on-demand Fargate base with Spot overflow under
prod; deployment circuit breaker with rollback; a real health-check grace period; RDS encryption, backups
and deletion protection under prod.

**i. CI/CD.** CodeBuild canonical. GitHub Actions reduced to plan-on-PR via **OIDC**, removing the static
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets. Deploy role scoped down from `PowerUserAccess` +
`iam:*`. The app's publish workflow fixed to resolve the real project id from SSM.

### 3. Cost Review

Drivers per environment, ranked, identifying which terms scale with pod count. Figures stated as list-price
estimates for one named region and **validated against the AWS pricing tooling while writing** — not
asserted from memory. Levers, given per-pod RDS is fixed: right-sizing (15 identical tasks is the largest
easy win), one otel-collector per environment rather than per pod, flavour-gated monitoring, log retention.
Where cost is traded against reliability, the trade is stated rather than buried.

### 4. Build & Rollout Plan *(replaces arch.md's Migration Plan — nothing is deployed)*

Zero to running, ordered so each step is independently verifiable: catalog and modules → bootstrap template
→ first `dev` environment stood up end to end → validate against the app's real QA path (sign in to the
console, load a storefront on a pod domain, confirm Cloud Map discovery and the Stripe webhook) → then
`staging`/`prod` flavours. Includes the app-side changes the new architecture requires — the stale
`fargate-config.yml` namespace/namespace-id defaults, and the publish workflow's project id.

### 5. Architecture Decisions

One record per decision in arch.md's required shape: current approach, proposed approach, why, benefits,
trade-offs, cost impact, and (since there is nothing to migrate) build impact. Covers: ECS Fargate over
EKS/App Runner; CloudFormation for bootstrap only; the service catalog; flavours; repo consolidation; state
and locking; per-pod RDS; per-pod NLB; CodeBuild over Actions; networking per flavour; Spot policy.
Rejected options recorded with reasons — EKS, App Runner, CDK, all-Terraform bootstrap, shared RDS,
shared `spg` fleet.
