00The one fact that reframes everything

Nothing is deployed. All three infrastructure repositories are unprovisioned legacy code. The requirements document was written assuming a running system, and therefore asks for a migration plan that minimises downtime, risk, resource replacement and data loss. None of those constraints exist. There is nothing to import, nothing to reuse, no downtime budget to protect.

So this proposal makes one substitution to the required structure: §4 is a Build & Rollout Plan — zero to running — in place of a Migration Plan. Everything else follows the brief exactly.

The second consequence is the more useful one: the target architecture is designed on its merits, rather than as a sequence of safe deltas from a system that must keep serving traffic.

This section is short and does one job: every defect below maps to a rule in §2, so the new architecture is answerable to something concrete rather than to taste.

Six ECR repositories are missing from bootstrap.yaml:187–253 for the same reason. ECR does not create repositories on push, so the image build fails before Terraform is ever reached.

RuleOne catalog, machine-read, drift-checked in CI.

b. Duplication

store-pod-cluster.tf is 654 lines because roughly 25 identical environment variables are copy-pasted into six service blocks. A new service costs about 60 lines of near-identical HCL.

RuleEnv computed once; services generated by for_each.

c. Two divergent deploy paths that disagree on the project id

  • Bootstrap / CodeBuild derives project as a random 4-character id.
  • GitHub Actions derives it as cksum(account-owner-region).

Different ids mean different SSM paths, different ECR paths, different state. The Actions path reads an SSM parameter only the bootstrap creates, and passes TF_VAR_env, TF_VAR_image_tag and TF_VAR_docker_registry — none of which cvhome-infra/params.tf declares, so all three are silently ignored. The application's own publish workflows use the cksum scheme, so images land in a registry path Terraform never looks at.

RuleOne deployer, one project id, resolved from one place.

d. No environment dimension

env is hardcoded "dev" in the SSM payload (bootstrap.yaml:451). One stack is one environment, and it can only ever be dev.

Ruleenv is a first-class parameter; a named flavour carries the rest.

e. Renames that broke routing and billing

  • The ALB forwards seller-ui.<domain> (store-core-lb.tf:96) and a Route53 record exists for it (:201) — but GatewayRouteLocatorImpl:68–70 matches only console-ui.<domain>.
  • The Stripe webhook is registered at /subscription/api/v1/stripe-webhook/public/events (bootstrap.yaml:805). That path did not survive the tenancy/billing split; the real one is /billing/api/v1/stripe-webhook/public/events.
  • The Stripe key is injected into tenancy, but Stripe now lives in billing.
RuleHostnames, routes and secret bindings derive from the catalog, not hand-maintained lists.

f. Dead knobs and dead wiring

  • pod_size is threaded SSM → pod object → module variable and never read — four values in the console that do nothing.
  • private_subnets is declared in cvhome-store-pod/params.tf:16 and referenced nowhere else in the repo.
  • random_password.password is generated (store-core.tf:4) and never referenced.
  • health_check, priority, service_type and load_balancer_host_matchers are declared in the shared module and consumed zero times.
  • cvhome-secrets is read by nothing, and its bcrypt() locals re-hash on every plan — a permanent diff if it were ever wired up.
RuleEvery input is consumed, or absent.

g. Reproducibility

Six module references are sourced git::…?ref=main. An apply can change behaviour with no commit in the repository being applied.

RulePin by tag — or, where a module has one consumer, keep it in-repo.

h. Security

  • Tasks run in public subnets with public IPs; every service sets public = true.
  • Service security groups allow ingress on ports 0–65535 from the whole VPC CIDR.
  • RDS is publicly_accessible = true — store-core-db.tf:54, store-pod-db.tf:54.
  • Both task roles grant s3:*, ssm:*, secretsmanager:*, logs:*, xray:* on "*" — ecs-task-roles.tf:35–38, :81–84.
  • The Terraform deploy role holds PowerUserAccess (bootstrap.yaml:992) and an inline iam:*.
  • GitHub Actions authenticate with static long-lived AWS access keys.

i. Reliability

  • FARGATE_SPOT at weight 100 with no on-demand base (ecs-service.tf:113), and desired = 1 for every service.
  • Deployment circuit breaker disabled, rollback disabled (:120–121).
  • health_check_grace_period_seconds = 0 (:110) on Spring Boot services that take tens of seconds to become healthy.
  • RDS with skip_final_snapshot, no backup retention, no deletion protection.

j. No right-sizing  ·  k. Stale identifiers in the application

All 15 services request an identical 512 CPU / 1024 MB / 1 task. Separately, fargate-config.yml:25–26 pins a real Cloud Map namespace and id — store-pod-507f1f77.cvhome.lcl and ns-je7qri6wn7fbsrpn — as checked-in defaults. Both must become environment-supplied.

02Target architecture

a. Platform: ECS Fargate + Cloud Map, kept — and now on the record

The brief explicitly opens the platform question, so this is a decision rather than an inheritance. It stays because the application is ECS-native, not because it is already there. ecs-service-discoveryclient resolves lb:// URIs through Cloud Map DiscoverInstances; there is a fargate Spring profile and a fargate-task-info module.

  • EKS adds a control-plane fee per cluster plus real operational weight, for no capability CVHome needs, and would require replacing the discovery client.
  • App Runner has no Cloud Map service discovery and cannot do the raw TCP 80/443 passthrough that spg requires for Caddy's on-demand TLS.

b. The service catalog — the central mechanism

One services.yaml is the single source of truth: name, layer, port, image repository path, whether it needs a database, health-check path, edge exposure, and any genuinely service-specific env. Terraform for_eaches it into ECR repositories, ECS services, task definitions, environment variables, security-group rules, ALB host rules and Route53 records. Common env is computed once into a local. The 654-line pod file becomes roughly 150. Adding a service is one catalog entry.

A CI job diffs the catalog against three sources in the application repository and fails on mismatch — common-config.yml for names and ports, fargate-config.yml for the service-ports map, and every build.gradle that sets an image name. That check is precisely what would have caught the four services that ended up with no infrastructure.

c. Flavours — the two-step model, made structural

Replace the scattered is_prod / is_monitoring / pod_auto_scale / pod_size flags with one named flavour: dev, staging, prod, ephemeral. A flavour fixes task sizing, desired counts, Spot-versus-on-demand policy, RDS class and backup policy, log retention, monitoring, and whether tasks run in private subnets. Every key stays individually overridable, and pod_size becomes real instead of dead.

StepToolDoes
1 · BootstrapCloudFormation, one clickCollects hosted zone, env name, flavour, project id, pod count/size, Stripe key. Writes the config record to SSM. Creates only what Terraform cannot create for itself — state bucket, scoped deploy role, CodeBuild projects — then starts the pipeline.
2 · ProvisionTerraform, run by CodeBuildprereq state (ECR + ACM, from the catalog) → image build → env state (everything else).
Why this fixes the one-click deploy

Nothing triggers CodeBuild in the legacy template. That is exactly why its “one-click” deploy stops halfway — the stack completes, and no infrastructure follows.

d. Environments, configuration and state

project becomes a stable, settable id rather than random 4 characters; env becomes a real parameter; resources are named ${project}-${env}-*. State lives at env/<env>/terraform.tfstate with S3 native locking (use_lockfile, Terraform ≥ 1.10) — no DynamoDB table, no extra cost. Configuration layers: SSM holds what bootstrap generated, envs/<env>.tfvars holds what humans chose, and tfvars wins. Someone who never touches git still gets a working environment; a team that does gets reviewable diffs.

The shared ECS module is absorbed rather than kept external and tag-pinned. It is where the reliability and IAM defects above actually live, it needs a near-rewrite, and it has exactly one consumer — so an external repository buys a release ceremony and nothing else.

f. Store-pod

Per-pod RDS, chosen for isolation over cost. The per-pod NLB is retained, and cannot be shared: spg terminates TLS itself, using Caddy on-demand certificates for arbitrary custom tenant domains. A shared NLB routes by port, not by SNI-to-backend mapping, and cannot express “this certificate, minted seconds ago, for a domain no configuration lists”.

Worth recording without proposing it now: a per-environment spg fleet backed by pod-registry would collapse those NLBs into one. That is an application change, and belongs to its own decision.

g. Secrets  ·  h. Security and reliability

RDS-managed master user secret; one Secrets Manager secret per concern under /${project}/${env}/; task IAM scoped to those ARNs. The Stripe secret binds to billing, and the webhook registers the path billing actually serves.

On networking cost specifically: NAT gateways are not enabled for dev or staging. They are poor value there, and VPC interface endpoints are not cheaper for this traffic mix. Prod pays for one NAT and gets private tasks — the trade is stated, not buried.

i. CI/CD

CodeBuild is canonical — Actions never applies again. GitHub Actions becomes a pure validation pipeline (.github/workflows/terraform-validate.yml): format, validate, lint, catalog-drift and CloudFormation checks on every push and pull request, plus a plan posted to the PR. Only the plan job touches AWS, and it does so via OIDC — the static AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY secrets go away entirely. The job breakdown is in §4, step 8.

The application's publish workflows are fixed at the same time, to resolve the real project id from SSM instead of cksum.

03Cost review

No dollar figures here yet — deliberately

The AWS pricing tooling is unavailable in this environment and querying prices from a local AWS session is out of scope for now, so any number here would be asserted from memory. That is exactly the failure mode this document exists to avoid. What follows is the cost structure, which does not depend on a price lookup.

What each environment is made of

Fixed per environment, independent of pod count: store-core ECS tasks (6 services), store-core RDS, the ALB, Route53, CloudWatch Logs, CodeBuild minutes, ECR storage across 15 repositories, Secrets Manager, and — under prod only — one NAT gateway.

Scaling linearly with pod count, which is the term that decides the bill:

TermShape
Per-pod ECS tasks9 services × task-hours × pods
Per-pod RDSinstance-hour + storage × pods
Per-pod NLBhourly + NLCU × pods
Per-pod CloudFrontrequests + egress × pods
Per-pod S3 (CDN + cert buckets)storage + requests × pods
Per-pod Cloud Map namespaceper-namespace + discovery calls × pods

A pod is therefore not a marginal cost — it is roughly a second small environment. Pod count is the single most important number in a flavour, and the architecture should make that visible rather than hide it behind a console dropdown.

Levers, ranked — given per-pod RDS is fixed

  1. Right-sizing. All 15 services request an identical 512 / 1024. A gateway, a Next.js UI and a JPA-heavy catalog service do not share a profile. Because task-hours appear once per service and again per pod, this is the largest single lever — and the catalog makes it a one-line change per service.
  2. One otel-collector per environment, not one per pod. The legacy code runs one in store-core and one in every pod — with N pods, that is N+1 collectors. Cross-namespace DNS resolves inside the VPC, so a single environment-level collector costs nothing in complexity and removes N tasks.
  3. Flavour-gated monitoring — off entirely below staging.
  4. Log retention from the flavour, rather than a hardcoded 14 days everywhere.
  5. No NAT below prod — saves the hourly charge and per-GB processing in the two environments that run most of the time.

Trades stated, not buried

  • Per-pod RDS costs materially more than a shared instance with a schema per pod. Bought for tenant isolation and per-pod restore.
  • On-demand Fargate base under prod costs more per task-hour than pure Spot. Bought because at desired = 1 on pure Spot, a reclamation is an outage.
  • One NAT gateway under prod is a real monthly line item, bought to get tasks out of public subnets — and not bought below prod, where narrowed security groups do the load-bearing work.

04Build & rollout plan

Replaces the brief's Migration Plan — nothing is deployed, so there is nothing to migrate. Ordered so that every step is independently verifiable before the next begins.

  1. Repo skeleton
    Terraform ≥ 1.10 pinned for native state locking; AWS provider pinned to an exact minor.
  2. Catalog + drift check
    services.yaml and scripts/check-catalog-drift.sh.
    Verify exits 0 against the current app checkout — and non-zero when a service is removed from it.
  3. Flavours
    flavours.yaml — dev, staging, prod, ephemeral.
  4. modules/ecs-service
    Absorbed and reworked: per-port security groups, flavour-driven capacity strategy, real grace period, circuit breaker with rollback, scoped task IAM.
  5. network, store-core, store-pod modules
    Services generated by for_each over the catalog; env computed once.

  7. Bootstrap template
    Rewritten to create only what Terraform cannot, and to start the pipeline.
    Verify clean under cfn-lint and cfn-guard before it is called done.
  8. GitHub validation pipeline

Application-side changes this architecture requires

Both live in the application repository, and both are load-bearing:

  • fargate-config.yml:25–26 — drop the pinned namespace and namespace-id defaults. Terraform already injects them; the checked-in values point at one specific pod in one specific account.
  • The two private-ECR publish workflows — replace the cksum project id with the real one resolved from SSM, and replace static credentials with OIDC. Today these push images somewhere Terraform never reads.

05Architecture decisions

Each in the shape the brief requires. “Build impact” replaces “migration impact”, since there is nothing to migrate.

ADR-1Platform: ECS Fargate + Cloud Map
Current
ECS Fargate, by inheritance rather than decision.
Proposed
ECS Fargate + Cloud Map, deliberately.
Why
The application resolves lb:// through Cloud Map and ships a fargate profile; spg needs raw TCP 80/443 passthrough for Caddy on-demand TLS.
Trade-offs
Less portable than Kubernetes; Fargate costs more per vCPU-hour than raw EC2.
Cost
Avoids an EKS control-plane fee per cluster.
Build
None — the target keeps the platform the code already assumes.
Rejected
EKS (cost and operational weight for no needed capability); App Runner (no Cloud Map discovery, no TCP passthrough); ECS on EC2 (capacity management CVHome does not want).
ADR-2CloudFormation for bootstrap only, Terraform for everything else
Current
CloudFormation bootstraps and also creates ECR, ACM and SSM; Terraform does the rest; the two disagree about the project id.
Proposed
CloudFormation creates only what Terraform cannot create for itself — state bucket, deploy role, CodeBuild — then starts the pipeline.
Why
The one-click launch is genuinely valuable and is CloudFormation's alone: no CLI, no state, no credentials to pre-provision. Beyond that boundary it buys nothing.
Trade-offs
Two languages in one repository.
Build
The template is rewritten, not extended.
Rejected
All-Terraform bootstrap (needs a pre-existing state bucket and credentials — kills the one-click experience); CDK (a third toolchain, and a build step before you can deploy).
ADR-3A machine-read service catalog
Current
Service lists hand-maintained in Terraform, CloudFormation and the application, independently.
Proposed
One services.yaml, for_eached into every derived resource, drift-checked in CI.
Why
The hand-maintained lists silently diverged and left four services with no infrastructure and six with no ECR repository.
Trade-offs
A layer of indirection between reading HCL and knowing what exists.
Cost
None directly — but it enables right-sizing, the largest cost lever.
Rejected
Generating the catalog from common-config.yml at plan time — couples an apply to the app repo's current state; the drift check gives the same safety without the coupling.
ADR-4Flavours instead of boolean flags
Current
is_prod, is_monitoring, pod_auto_scale, pod_size (dead), allow_test_stores.
Proposed
One named flavour per environment fixing sizing, capacity policy, RDS class, backups, retention, monitoring and networking; each key overridable.
Why
Booleans multiply combinatorially and encode no intent — four independent flags is sixteen configurations nobody has tested.
Trade-offs
An unusual combination requires an explicit override.
Build
pod_size becomes real instead of dead.
ADR-5Repository consolidation, including the shared ECS module
Current
Five repositories; six module references pinned to main.
Proposed
One cvhome-platform. The shared module absorbed as modules/ecs-service/; cvhome-secrets deleted.
Why
The shared module has exactly one consumer and needs a near-rewrite; an external repo buys a tag-and-release ceremony per change and nothing else. ?ref=main means an apply can change behaviour with no commit.
Trade-offs
The module can no longer be shared with a future second consumer without extraction.
Rejected
Keeping it external and tag-pinned — the original position, reversed once it became clear the module needed rewriting, not pinning.
ADR-6State layout and S3 native locking
Current
One state file, keyed differently by CodeBuild and by Actions; no locking.
Proposed
env/<env>/terraform.tfstate and prereq/<env>/…, with use_lockfile = true.
Why
One state per environment is the unit that gets created and destroyed; native locking removes a DynamoDB table.
Trade-offs
Requires Terraform ≥ 1.10.
Build
None — no state exists to move.
ADR-7Per-pod RDS
Proposed
Unchanged from today, now deliberate.
Why
Tenant data isolation at the instance boundary; a noisy pod cannot starve another.
Trade-offs
The dominant term that scales with pod count.
Cost
Highest per-pod line item — accepted, with levers taken elsewhere.
Rejected
One shared RDS with a schema per pod — cheaper, but couples tenant blast radius and restores.
ADR-8Per-pod NLB
Proposed
Unchanged, with the reason recorded.
Why
spg terminates TLS with Caddy on-demand certificates for arbitrary custom tenant domains; a shared NLB cannot express that mapping.
Cost
Second-largest per-pod term.
Rejected
For now: a per-environment spg fleet backed by pod-registry — it would collapse these NLBs, but it is an application change and belongs to its own decision.
ADR-9CodeBuild canonical, Actions plan-only
Current
Two deploy paths that disagree on the project id; Actions passes three variables Terraform does not declare; static AWS keys in GitHub secrets.
Proposed
CodeBuild applies; Actions runs fmt, validate, lint, drift and plan-on-PR via OIDC.
Why
One deployer means one project id and one state.
Trade-offs
Applies happen in AWS, so the log lives in CodeBuild rather than the PR.
Build
The application's publish workflows must be fixed at the same time.
ADR-10Networking per flavour
Current
Tasks in public subnets with public IPs, no NAT, RDS publicly accessible.
Proposed
Prod runs tasks in private subnets behind one NAT; dev and staging keep public subnets; RDS is never publicly accessible in any flavour.
Why
The security gap that matters most is the publicly reachable database, and closing it costs nothing. Private tasks cost real money, so they are bought where they matter.
Trade-offs
Dev and staging tasks keep public IPs; the narrowed security groups do the load-bearing work there.
ADR-11Spot policy
Current
FARGATE_SPOT weight 100, no on-demand base, desired = 1, circuit breaker disabled.
Proposed
An on-demand base with Spot overflow under prod; Spot-heavy below it; circuit breaker with rollback everywhere.
Why
At desired = 1 on pure Spot, a reclamation is an outage — and with the circuit breaker off, a bad task definition never rolls back.
Cost
An increase under prod, stated deliberately.
